🧪 Laya + SOC — Demo: setup → install → configure → validate

2026-09-27 · end-to-end walkthrough of the deployed pattern (laya 0.3.20) · every expected output below is real, measured on this stack

0 · What you'll build

A decision sidecar beside the live SOC: gemma keeps deciding (shadow mode), Laya answers the same questions and logs everything to laya-shadow.jsonl. After the soak gate passes, a one-line env flip moves decisions to Laya with confidence-gated fallback. Total footprint: 4.7 GB RAM on each host, zero GPU.

1 · Setup — what you need before touching anything

Host 2 (decision traffic)edge host (runs wazuh + ingest + mail)Laya must sit next to its callers (loopback-only)
Python≥3.10 (3.12.3 used)venv per host
Ports8099 (laya-serve, loopback) · 8765 (ingest, edge host)8000 default avoided on purpose
Disk~5 GB venv + 2.3 GB checkpointsCPU torch wheel saves ~5 GB
NetworkHF reachable once (preload), offline afterHF_HUB_OFFLINE=1 at runtime
Decision to make up front: which questions each part answers (the question set) and where its truth comes from (deterministic rule vs LLM verdict). The SOC contract lives in soc-agents/soc-triage/IDENTITY.md. If you can't state the decision contract in one sentence, don't wire the hook yet.

2 · Install (control host first, then replicate)

2.1 venv + CPU torch + laya — order matters

python3 -m venv /home/operator/laya/.venv
/home/operator/laya/.venv/bin/python -m pip install --upgrade pip
# CPU-only torch FIRST (PyPI default pulls multi-GB CUDA):
/home/operator/laya/.venv/bin/python -m pip install torch --index-url https://download.pytorch.org/whl/cpu
/home/operator/laya/.venv/bin/python -m pip install "laya[serve]"
# verify
/home/operator/laya/.venv/bin/python -I -c "import laya; print(laya.__version__)"   # → 0.3.20

2.2 Preload checkpoints (needs HF network this once)

export HF_HOME=/home/operator/laya/hf-cache
/home/operator/laya/.venv/bin/python -c "from laya import Router; Router(preload=True)"
# → all 3 checkpoints (english, multilingual, typed-decisions), 2.3 GB total

2.3 systemd user unit

# ~/.config/systemd/user/laya-serve.service (full text: laya-control/systemd/)
systemctl --user daemon-reload
systemctl --user enable --now laya-serve.service
journalctl --user -u laya-serve -f        # expect: "3 models loaded" then uvicorn on 127.0.0.1:8099

2.4 Replicate to edge host (proven cross-host rsync)

rsync -a /home/operator/laya edge host:/home/operator/laya        # ~3.5 GB incl venv — same abs paths, python 3.12 both
scp ~/.config/systemd/user/laya-serve.service edge host:~/.config/systemd/user/
ssh edge host 'sed -i "s/LAYA_THREADS=8/LAYA_THREADS=6/" ~/.config/systemd/user/laya-serve.service'  # edge host has 6 usable threads
ssh edge host 'systemctl --user daemon-reload && systemctl --user enable --now laya-serve && loginctl enable-linger operator'

linger matters — user units die at logout without it. edge host system services need sudo; laya-serve is a user unit (mixed model, that's fine).

3 · Configure

3.1 laya-serve (env-vars only — no CLI flags exist)

EnvValueNote
LAYA_HOST / LAYA_PORT127.0.0.1 / 8099loopback-only; set LAYA_API_KEY before ever exposing
LAYA_DEVICEcpu
LAYA_PRELOAD1all 3 ckpts at boot, 4.7 GB RAM
LAYA_THREADS8 (control host) / 6 (edge host)≤ physical cores, oversubscription regresses hard
LAYA_AUTO_TASK0explicit routing, not auto
HF_HOME / HF_HUB_OFFLINE/home/operator/laya/hf-cache / 1offline works only after preload (§2.2)

3.2 Flip the SOC services into shadow mode

# edge host — one line each, created if absent (that's why the first test logged nothing!)
sudo -n tee /etc/default/realtime-soc-server <<'EOF'
# Laya shadow mode (Phase 1): off|shadow|gated. shadow = log-only, LLM verdict still wins.
LAYA_MODE=shadow
EOF
sudo -n tee /etc/default/imap-watcher <<'EOF'
# Laya shadow mode (Phase 1): off|shadow|gated. shadow = log-only, mail routing unchanged.
LAYA_MODE=shadow
EOF
# restart the system units (sudo) and verify
sudo -n systemctl restart realtime-soc-server imap-watcher
ssh edge host 'grep LAYA /etc/default/realtime-soc-server /etc/default/imap-watcher'

3.3 The hooks (code side — deploy once, they're in prod)

# shadow client: /opt/soc-openclaw/lib/laya_shadow.py (stdlib-only, never raises)
# hook 1: realtime_ingest.ingest_wazuh_alert  → 4 triage questions (v1.1: 3 + deterministic severity)
# hook 2: imap-watcher._process_one          → 3 email questions
# backups before every patch: file.bak-laya-YYYYMMDD · py_compile after every edit · RESTART then verify

Rule learned twice: patch → compile → restart → verify. An E2E test against a stale process looks like a failure that isn't one.
